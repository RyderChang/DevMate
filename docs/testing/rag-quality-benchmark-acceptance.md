### 失败请求 usage 采集缺口

PR 审查指出：[RagService](../../devmate-server/src/main/java/com/devmate/conversation/service/RagService.java) 在网关正常返回后先调用 [RagTransactions.receipt](../../devmate-server/src/main/java/com/devmate/conversation/service/RagTransactions.java)，再进行输出校验。因此 `RAG_OUTPUT` 失败可能已有持久 usage；提供商解析失败则可能没有 receipt。统一 502 本身无法区分，应该在清理前按请求 UUID 联查持久 `chat_state`、调用状态及三个 token 字段。

原采集脚本只保存公开响应，没有提取这三条失败 invocation 的持久状态或 usage；隔离数据库已清理，也没有可核验的数据库快照。这是**未满足冻结用量采集要求的遗留缺口**，不是已证明“所有失败都未收到 usage”。现存 API 结果无法补回三条用量或确认逐题失败阶段，完整 token 总量和实际账单仍待所有者的原始提供商记录；[后续阶段诊断](rag-failure-stage-and-quality-assessment.md)的新请求也不能替代旧请求。不得用成功样本、估费或重新调用模型补造历史数据。

### 超出核心问题的断言和引用质量

- **Q1** 回答额外称文档检索 API 的未知请求字段会被拒绝为 400。返回的检索合同只写 400 `INVALID_PARAMETER`，未知字段规则出现在 RAG 对话合同；这句话无法由所引文档直接支持，存在接口混淆。E1、E2 本身仍正确。
- **Q2** 回答正确引用 score 定义与预算造成的 `incomplete`，但又把固定 query/topK 边界、请求失败和 UNKNOWN 等列作 `incomplete` 的成因。引用资料不能证明这些情形会返回 `incomplete=true`；其中请求失败属于错误结果，需与成功检索响应的完整性字段区分。来源变化有对应状态，但回答把多种情形合并为同一因果结论，证据不足。
- **Q5** E9 有直接引用 C1/C4；另返回的 C5 为需求基线的阶段说明，不直接支持“最近索引失败仍保留旧活动代”，属多余引用。
- **Q10** 正确没有编造点数，但将 README 中“Qdrant 文档索引和本地 Embedding 默认关闭”概括为“Qdrant 默认关闭”，措辞扩大了对象；不影响弃答结论。

因此，**检索总体较高但并未覆盖全部冻结证据；成功回答的核心事实均有可定位引用，但生成可用性和附加断言质量尚不足以判为全面充分**。三次 502 的统一错误也可能来自 DeepSeek 响应结构、结束原因、usage 校验或 RAG 输出 Schema/业务校验；公开 API 响应不含原始模型输出，不能据此确定具体失败环节，更不能归因于 Q4 的 E7 缺失。

配对显式检索命中与成功引用完全对应，只证明这些**已引用**来源的位置和内容；RAG 内部再次检索时未引用的候选、最终提供给模型的完整片段集及原始提供商 JSON 均不可观测，不能宣称两次检索的全体候选相同。
