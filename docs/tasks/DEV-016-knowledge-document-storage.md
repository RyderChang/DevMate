## 5. 模块与存储职责

### 5.1 knowledge 与对象存储边界

- `knowledge` 应用服务负责鉴权、上传编排、额度、幂等、状态转换与删除，不包含提供商 SDK 类型。
- 项目归属通过 project 的公开应用服务验证；当前用户从认证上下文取得，不能从请求接受 `ownerUserId`。
- 定义最小内部存储接口，表达写入、受限读取、存在性/完整性核对与幂等删除；适配器封装 SDK、超时和安全异常。
- 未找到对象可作为删除成功；鉴权失败、网络错误、超时不能伪装成不存在。
- bucket 与对象 key 仅供内部使用。key 由服务端按用户、项目、文档 ID 和不可猜测标识生成，数据库保存精确定位。
- 文件名、客户端 MIME、客户端路径均是不可信数据。用户不能指定 endpoint、bucket、key 或公共访问策略。
- 不建立无调用方的通用文件中心；不新增跨模块 Mapper 访问，不把远程调用放入数据库事务。

### 5.2 各存储的职责

| 存储              | 本任务职责                                                                   | 禁止混入的职责                                     |
| ----------------- | ---------------------------------------------------------------------------- | -------------------------------------------------- |
| MySQL             | 文档归属、原文件元数据、校验和、对象定位、状态、请求幂等、额度预留和补偿记录 | 不保存文件二进制、全文或凭据                       |
| MinIO/S3 兼容存储 | 保存原始字节，私有访问；应用以完整性校验确认存储结果                         | 不作为权限或生命周期真相源，不生成公开链接         |
| Redis             | 本任务不使用                                                                 | 不以易失锁或缓存取代数据库状态和容量约束           |
| Qdrant            | 后续任务再接入                                                               | 不创建 collection、向量、占位索引或 embedding 调用 |

校验 UTF-8 时允许流式扫描，但不渲染 Markdown、不抓取链接、不执行内容、不提取语义或生成分块。
原文件按上传字节保存；SHA-256 以原始字节计算，不把 S3 ETag 当成通用 SHA-256。
文档仍是不可信输入，未来解析或 RAG 不能让其覆盖系统指令。

## 6. 数据模型与生命周期

### 6.1 元数据和约束

使用 `knowledge_documents` 保存下列信息；具体 DDL 和索引在实现 PR 中按本节约束审查，不在本次创建 migration：

- `id`、`owner_user_id`、`project_id`，沿用自增 BIGINT；不新增另一套 ID 方案。
- 安全展示文件名、受认可的文件类型、实际字节数、SHA-256、来源类型 `UPLOAD`。
- 私有 bucket/key、存储状态、受控失败码、创建/更新时间；时间按 UTC 保存和 ISO 8601 输出。
- 上传请求 UUID、请求指纹、操作版本或租约、补偿次数与下次执行时间；必要时使用独立操作表保持职责清晰。
- 项目级容量预留记录或等价的事务串行化约束；并发上传不能仅在事务外“先查数量再插入”。

请求唯一性按 `(owner_user_id, project_id, client_request_id)` 约束，包含并发重复的数据库兜底。
指纹覆盖规范化文件名、文件类型、实际字节数和 SHA-256；不能仅凭同名判定同一次请求。
查询固定携带用户、项目与可见状态；列表索引匹配归属过滤与排序，补偿索引匹配状态和到期时间。
明确用户、项目外键及归属一致性保障，不使用数据库级对象存储级联删除。

新增下一个 Flyway migration，当前基线预计 V6；实现前重新确认编号。V1 至 V5 不得修改、重命名或格式化。
从空 MySQL 8 顺序迁移验证约束，拒绝未知状态、负字节数与非法计数；不得以 H2 代替兼容性验证。

### 6.2 状态与跨存储一致性

状态为 `UPLOADING`、`STORED`、`FAILED`、`DELETE_PENDING`。`STORED` 仅表示原文件已存储。
不使用 `READY`、`INDEXED` 等可能暗示已解析或已向量化的状态。

上传流程：

1. 校验认证、项目归属、参数与文件，流式计算实际长度和指纹；受限临时文件只放在受控目录，请求结束清理。
2. 短事务再次验证项目可用性，原子检查幂等与容量、预留额度并保存 `UPLOADING` 及唯一对象 key。
3. 事务外上传对象，配置连接、读取与总操作超时；不无界缓冲文件，不启用不可见的无限重试。
4. 短事务通过状态和操作版本条件更新为 `STORED`，再次确认项目有效；提交成功后才返回成功。
5. 结果不确定时保留 `UPLOADING` 并安排核对；确定不可完成才转 `FAILED`，随后仅允许清理。
   数据库暂不可写时依赖步骤 2 已提交的记录恢复，不假称异常处理已持久化；确认对象不存在且无迟到写入之前不得释放容量或丢弃定位。

必须覆盖“写入成功但响应超时”“对象成功但数据库更新失败”“请求进程崩溃”“项目在上传期间被删除”。
补偿记录与对象 key 必须先于远程写入持久化，禁止只有内存队列或仅在异常 catch 中删除文件。
恢复 `UPLOADING` 时先核对对象和完整性；对象完整且项目有效才转 `STORED`。
对象确定缺失且无在途写入，或确定完整性不符时转 `FAILED`；核对仍超时/不可用则保留 `UPLOADING`，
达到自动尝试上限后标记需人工处理，不把未知结果伪装成确定失败。扫描器不重新上传原文件。
旧上传返回不能覆盖新的删除状态；清理器与上传请求必须通过租约/条件更新避免竞态，并处理迟到的写入。

状态转换与同 UUID、同指纹重放约定（均先校验当前项目与用户）：

| 当前状态/情形                                 | 允许的转换与处理                                                          | POST 重放结果                                         |
| --------------------------------------------- | ------------------------------------------------------------------------- | ----------------------------------------------------- |
| 尚未预留：校验或容量拒绝                      | 不创建文档或请求映射，不写对象                                            | 按本次请求重新校验，不视为已接入失败终态              |
| `UPLOADING`，包括写入超时、提交结果未知或崩溃 | 完整性确认后转 `STORED`；确定不可完成转 `FAILED`；删除转 `DELETE_PENDING` | 409，表示尚未确认；保留原 UUID，禁止因超时自动换 UUID |
| `STORED`                                      | 仅删除可转 `DELETE_PENDING`                                               | 200，返回原文档，不再次写对象                         |
| `FAILED`                                      | 不得恢复为 `UPLOADING`/`STORED`；仅清理，或由删除转 `DELETE_PENDING`      | 409，稳定终态；另一次接入必须使用新 UUID              |
| `DELETE_PENDING`                              | 仅继续清理，不得重新可见                                                  | 409；DELETE 重试仍为 202                              |
| 已清理的失败/删除请求映射                     | 清理完成起保留 24 小时，之后物理删除映射                                  | 窗口内 409；过期后按新请求校验和预留                  |

`FAILED` 在清理完成前可显示安全失败码，仍占用额度；清理完成后物理移除文档，只保留最小幂等终态。
首次 503/504 是本次 HTTP 操作结果，不单独决定数据库终态。调用方应使用原 UUID 和原文件确认；
核对后允许同 UUID 从“处理中 409”变为成功 200，已提交的 `FAILED` 则始终不可恢复成功。
数据库条件更新必须同时校验状态与操作版本。数据库租约过期不证明远端 PUT 已停止；
无法证明没有迟到写入时保留对象定位与容量，交由继续核对或人工处理，不得仅凭一次 HEAD 不存在就清账。

删除流程：

1. 短事务验证归属，标记 `DELETE_PENDING`，立即从普通列表/详情隐藏，取消后续消费资格。
2. 事务外删除对象；不存在视为已完成，超时保持待处理。
3. 确认无仍可写入的上传操作后，事务内释放额度、清理文档元数据并保留有界幂等终态。

项目软删除后，所有文档 API 立即不可访问；补偿扫描需发现其残留文件并纳入相同清理流程。
通过 project 公开的内部查询边界或事务内持久化交接实现，禁止通过跨模块 Mapper、无凭证回调或仅内存事件完成。
项目删除仍不得因远程存储阻塞数据库事务。清理后不承诺恢复原文件，存储备份的保留范围需在运行说明中单独声明。

### 6.3 有界恢复参数

补偿先实现 knowledge 内部最小扫描器，不引入 Redis、消息队列或独立 Worker。每 60 秒扫描、
每批最多 50 条；失败后最多 5 次自动重试，依次退避 1/2/4/8/16 分钟；耗尽后保留原状态、定位和额度，交由受控运维重试。
恢复阈值必须大于上传总超时并留出余量；上传恢复须在租约到期后领取，不能删除正常上传中的对象。租约必须可被多个实例安全抢占。
上传总超时 30 秒、操作租约 2 分钟、实例并发上传上限 4；均需配置校验及确定性测试。
以上是已确认的默认参数，不把“每分钟扫描”写成“一分钟内必然物理删除”的 SLA。
提供只输出 ID、计数和受控错误码的处理说明；不开放未鉴权的清理或故障注入 API。

## 7. API 契约

保持现有无 `/api` 前缀的路径风格；所有接口要求 JWT 和 `user` authority，管理员默认不能绕过所有权。

| 方法与路径                                            | 输入及预期结果                                                                                                                           |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /projects/{projectId}/documents`                | `multipart/form-data`，一个 `file` 与 UUID `clientRequestId`；成功返回 200 和 `Result<DocumentResponse>`，只在 `STORED` 已提交后成功     |
| `GET /projects/{projectId}/documents`                 | 默认 `page=1&pageSize=20`，页码 `1..10000`、页大小 `1..100`；`Result<PageResult<DocumentResponse>>`，按 `create_time DESC, id DESC` 排序 |
| `GET /projects/{projectId}/documents/{documentId}`    | 返回当前用户项目内可见文档元数据，不返回正文或对象定位                                                                                   |
| `DELETE /projects/{projectId}/documents/{documentId}` | 接受删除后返回 202 与统一响应，表示等待物理清理；所有者对同一待删除记录重试仍为 202，已清理或不存在为 404                                |

`DocumentResponse` 包含 `id`、`projectId`、展示文件名、类型、实际字节数、来源、存储状态、
受控失败码、创建/更新时间。不返回 bucket/key、内部 endpoint、签名 URL、异常堆栈或原始 SDK 响应。
分页可展示 `UPLOADING`/`STORED`/`FAILED`，不能把失败文件显示成上传成功。

幂等约定：同 UUID、同指纹且已成功返回原文档；处理中返回 409，不再次写入；
同 UUID、不同指纹返回 409；已提交 `FAILED` 或删除状态的请求在保留窗口内返回稳定冲突，重新上传需要新 UUID。
超时后仍为 `UPLOADING` 的请求遵循第 6.2 节，不能仅根据一次 503/504 当作失败终态。
重放也必须先验证当前项目与用户，不得借请求映射访问已删除项目。窗口到期后的行为要在 OpenAPI 写明。

错误要求：

- 无认证 401、缺少 authority 403；不存在、他人或已删除项目统一 404。
- 文档不存在、跨用户、项目路径错配或已删除统一 404；同一所有者对 `DELETE_PENDING` 重复 DELETE
  按上表返回 202。不以存储错误泄露存在性。
- 非法 ID、UUID、编码、空内容、文件名和 multipart 形状返回安全 400；大小超限 413，不支持格式 415。
- 容量不足、幂等冲突、状态冲突返回 409；实例并发保护返回 429。
- 功能关闭、对象存储不可用返回安全 503；远程操作超时返回 504。失败不会返回伪成功。
- 在现有 `ErrorCode` 中补充语义枚举并保持既有数字 code 风格，不借本任务重构全站错误模型。
- multipart 容器层拒绝也必须经统一错误处理；确认响应不携带临时路径或请求正文。

## 8. 配置与安全边界

知识上传默认关闭；关闭时上传返回安全 503，不要求对象存储凭据，既有认证、项目和对话继续工作。
元数据读取维持归属校验；关闭期间可标记删除，但物理清理暂停，重新启用后恢复，不能丢失待处理记录。

启用时验证 endpoint、region、bucket、访问凭据、大小/容量/并发/超时/扫描限制，并在后端 README 列出准确环境变量。
凭据只从服务端环境注入，不写入源码、前端、测试固定值或日志；CI 临时凭据运行时生成。
生产要求 HTTPS；本地隔离测试允许显式 HTTP。endpoint 由部署者配置，不接受请求覆盖。
bucket 由开发/部署流程创建并保持私有，应用不隐式建立公开 bucket、不修改公共访问策略。

扩展名与客户端 MIME 仅作辅助校验，还要验证实际文本编码、长度和禁止字节；无法可靠判定的二进制拒绝。
Markdown 中的 HTML、脚本和外链仅按不可信文本存储；未来渲染另立任务处理。
日志仅记录 traceId、资源 ID、操作、状态、耗时和安全错误码，不记录文件名、正文、凭据或完整 SDK 请求。
临时落盘限制目录、容量和生命周期；崩溃遗留清理只操作可确认属于本应用的临时文件，不能清理任意系统路径。

## 11. 实施顺序、回滚与交付
