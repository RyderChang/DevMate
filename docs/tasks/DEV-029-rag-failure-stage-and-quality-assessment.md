# DEV-029：RAG 502 阶段证据与分项质量评估

日期：2026-10-09。基线：本机 `origin/develop`（远端刷新因连接重置失败，交付前须再次核对）。前置证据为 DEV-027 固定题集和 DEV-028 分项诊断；两者的 PR 尚未合并，不改写其原始结果。

## 目标与顺序

1. 在 RAG invocation 的持久记录中增加脱敏的 502 失败阶段及安全类别，保留原有公开错误码、幂等与 usage 语义。
2. 先用 Stub 回归验证 DeepSeek 网关、RAG 输出校验及持久化，取得可区分的阶段证据。
3. 验证通过后，在用户授权的 **最多 3 次、总费用不超过人民币 2 元** 范围内复测 Q4、Q6、Q9，逐题记录新请求的阶段；历史三次 502 的根因仍以“未知”标注，不将新请求归因为旧请求。
4. 随后分别评估 Q4 的检索排序和成功回答的逐断言引用约束。只形成证据与修复建议，本任务不调整排序、提示词或引用校验策略。

## 持久证据合同

- 新 Flyway migration 给 `rag_invocation_details` 增加两个可空字段：`failure_stage` 和 `failure_category`。二者必须同时为空或同时为固定、受约束的枚举值；仅在已持久化的 RAG 502 失败上填写。
- 阶段区分 `PROVIDER_HTTP`、`PROVIDER_RESPONSE`、`RAG_OUTPUT`；类别使用由代码指定的有限安全值，至少区分 HTTP 非预期状态、提供商信封/正文/结束原因/用量问题、RAG JSON 结构和引用问题。不记录原始响应、模型正文、提示词、密钥、异常 message 或上游错误体。公开 API 不暴露诊断字段。
- 在原有失败事务中原子写入阶段/类别和失败状态；成功记录与非 502 失败保留 NULL。失败记录重放不得再次调用模型或覆盖已保存诊断。数据库提交无法确认时仍按既有 `STATE_UNCONFIRMED` 处理，不伪称证据已保存。
- Stub 回归覆盖同一公开 502 对应不同阶段、诊断字段的固定值与脱敏、usage 在已接收响应后仍保存、幂等重放。MySQL 8 / Testcontainers 验证迁移和约束。

## 复测与评估标准（运行前冻结）

- 复测仅对 DEV-027 公开七文档隔离环境中的 Q4、Q6、Q9 各一次；保留新 UUID，不重放旧 UUID。先核对官方单价、请求上限及预计 token 成本；无法确定不超过 2 元则不发起。密钥仅本机隐藏输入与临时进程环境，不写入仓库、报告或终端输出。记录 HTTP 状态、数据库阶段/类别、是否有 receipt/usage、检索候选 ID，不保存原始回答正文到 Git。容器按独占标签清理。
- Q4 排序只检查冻结问题、E7/E8 证据槽和相同七文档索引。DEV-028 的扩大 topK 记录中 E7 排名 19、score 0.403412 是待复核基线；计算 top-5/top-20 命中和目标位置，区分过滤、索引、相似度排序。探索性改写查询只能另标诊断，不能冒充固定题集提升。
- 逐断言引用只审 DEV-027 已成功的回答及本次成功复测；将每句拆成可验证的原子断言，逐项标记“支持 / 证据不足 / 与来源冲突 / 非事实性措辞”，记录所引片段与应有证据槽。引用 ID 合法或 JSON 合法本身不等于断言获支持。对 Q1、Q2、Q5、Q10 的已知问题逐项复核，并评估可机器约束与须由评测/人工判定的边界。
- 证据等级：确定性代码、数据库状态或保留的原始评测记录为“确认”；新复测只证明新请求；从兼容现象推断旧请求为“可能”；缺少区分性材料为“未知”。分别报告三次 502、Q4 排序和断言引用，不给单一笼统结论。

## 验收与边界

- 先提交本任务书，再改代码。缺陷回归测试先于实现；不调用真实付费模型执行 CI。最小充分测试通过，文档链接与 `git diff --check` 通过。
- 最终报告列出实际请求次数和估计费用、每题状态与阶段、持久证据查询方式、排序数据、逐断言表、未确认事项。若无法运行复测，应说明原因和可执行命令；不能以 Stub 推断历史三次 502 的根因。
- 本任务不部署、不更改用户项目数据、不修改已执行 migration、不合并 PR。PR 面向 `develop`，由所有者审核。回滚为撤销代码并以新 migration 移除新增诊断列，已有失败状态/usage 不受影响。
